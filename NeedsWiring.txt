============================================================
SANDLOT PICKS — SERVER-SIDE WIRING REQUIREMENTS
============================================================

This document describes the frontend features that are currently
running on mock data / localStorage and need real backend support.
Each section is self-contained — copy any one section into a
server-side chat to scope and build that feature in isolation.

Existing API conventions (already in use by the app):
  - Base URL prefix: /api/v1
  - Auth: JWT Bearer token in Authorization header
  - Error responses: { "detail": "<human-readable string>" }
    Frontend reads err.message (mapped from response.detail)
  - User profile lives at GET /api/v1/users/me
  - Subscriptions namespace: /api/v1/subscriptions/...
  - Admin namespace: /api/v1/admin/...

Project: React 18 + Create React App, Supabase as content DB,
Stripe for billing. Server is Python/FastAPI based on existing
endpoint shape.


============================================================
FEATURE 1 — ALERTS / NOTIFICATIONS SYSTEM
============================================================

WHAT IT IS
----------
Admins can publish alerts that either (a) pop up as a modal the
next time the targeted user signs in, or (b) silently land in
the user's inbox on their settings page. Alerts can be sent to
all users or to a specific list of email addresses.

CURRENT STATE
-------------
All alert data lives in browser localStorage under keys
`spa_admin_alerts_v1` and `spa_admin_alerts_read_v1`. This means
targeted-email alerts don't actually reach the right user since
the data never crosses browsers. Needs a real backend.

FRONTEND FILES THAT WILL CONSUME THIS API
-----------------------------------------
- src/data/constants/alertsMockData.js   (swap helpers for fetch calls)
- src/components/AlertSignInModal.jsx     (auto-pops on login)
- src/components/AlertInbox.jsx           (settings page inbox card)
- src/components/pages/Admin/AlertComposerModal.jsx (admin composer)

DATA MODEL
----------
Table: alerts
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid()
  subject         text NOT NULL
  body            text NOT NULL
  display_type    text NOT NULL CHECK (display_type IN ('modal', 'general'))
  target_type     text NOT NULL CHECK (target_type IN ('all', 'specific'))
  target_emails   text[] NOT NULL DEFAULT '{}'
                  -- only populated when target_type = 'specific'
  created_at      timestamptz NOT NULL DEFAULT now()
  created_by      uuid REFERENCES users(id)
  expires_at      timestamptz NULL  -- optional; treat NULL as "no expiry"

Table: alert_reads
  alert_id        uuid REFERENCES alerts(id) ON DELETE CASCADE
  user_id         uuid REFERENCES users(id)  ON DELETE CASCADE
  read_at         timestamptz NOT NULL DEFAULT now()
  PRIMARY KEY (alert_id, user_id)

Index: alert_reads(user_id) for fast per-user lookups.

ENDPOINTS
---------

(1) POST /api/v1/admin/alerts
    Auth: admin only (403 otherwise)
    Body:
      {
        "subject": "Brief outage tonight",
        "body": "We're pushing a deploy at 11pm ET. ~30 min downtime.",
        "display_type": "modal",                  // 'modal' | 'general'
        "target_type": "all",                     // 'all'   | 'specific'
        "target_emails": ["a@b.com", "c@d.com"]   // empty array when target_type='all'
      }
    Validation:
      - subject and body required, both non-empty
      - if target_type = 'specific', target_emails must have ≥1 valid email
    Response 201:
      {
        "id": "uuid",
        "subject": "...",
        "body": "...",
        "display_type": "modal",
        "target_type": "all",
        "target_emails": [],
        "created_at": "2026-04-28T15:00:00Z",
        "created_by": "uuid"
      }
    Errors:
      400 { "detail": "Subject is required." }
      400 { "detail": "At least one recipient email is required." }
      403 { "detail": "Admin access required." }

(2) GET /api/v1/admin/alerts
    Auth: admin only
    Returns: array of all alerts (full objects, newest first), most recent 100.
    Used for: future admin "manage existing alerts" view.

(3) DELETE /api/v1/admin/alerts/:id
    Auth: admin only
    Returns: 204 No Content on success
    Errors: 404 { "detail": "Alert not found." }

(4) GET /api/v1/users/me/alerts
    Auth: any authenticated user
    Server-side filtering — NEVER return alerts not targeted at the user.
    SQL pattern:
      SELECT a.*, ar.read_at IS NOT NULL AS is_read
      FROM alerts a
      LEFT JOIN alert_reads ar ON ar.alert_id = a.id AND ar.user_id = :user_id
      WHERE (a.target_type = 'all'
             OR :user_email = ANY(a.target_emails))
        AND (a.expires_at IS NULL OR a.expires_at > now())
      ORDER BY a.created_at DESC
    Response:
      [
        {
          "id": "uuid",
          "subject": "...",
          "body": "...",
          "display_type": "modal",
          "created_at": "2026-04-25T16:30:00Z",
          "is_read": false
        },
        ...
      ]
    Note: do NOT return target_type or target_emails to non-admin users.
    The is_read flag drives the unread badge + sign-in modal queue.

(5) POST /api/v1/users/me/alerts/:id/read
    Auth: any authenticated user
    Marks a single alert as read by the current user.
    Response: 204 No Content
    Idempotent — second call is a no-op.
    Errors: 404 if alert not visible to this user (don't leak existence).

CLIENT BEHAVIOR TO BE AWARE OF
------------------------------
- On every successful login, the client immediately calls (4) and
  filters for `display_type === 'modal' && !is_read`. Those pop as
  a queued modal sequence; user clicks "Got it" → call (5).
- The settings inbox calls (4) on mount and re-renders unread badge
  off the `is_read` flag.

OPEN QUESTIONS
--------------
- Soft delete for compliance? (recommended: add `deleted_at`)
- Rate limit (5)? Probably not needed — but add basic auth-protection.

FEATURE 1A — ALERT READ RECEIPTS (ADMIN VIEW)
============================================================

WHAT IT IS
----------
Admins want to see who has acknowledged each modal alert (clicked
"Got it" on the sign-in modal). This drives two UI states in the
Alert Manager section of the admin dashboard:

  1. target_type = 'all'      → show "{N} of {audience_size} confirmed"
  2. target_type = 'specific' → show per-recipient list: which targeted
                                emails have clicked "Got it" and when

Inbox / "general" alerts are out of scope here — read_at on those is
just an "opened" signal, not an explicit acknowledgement.

CURRENT STATE
-------------
The alert_reads table already exists (created in the original Feature
1 server build) and is populated by POST /api/v1/users/me/alerts/{id}/read
when a user dismisses the sign-in modal. The data is captured but no
admin endpoint surfaces it. The Alert Manager UI at
src/components/pages/Admin/AdminPage.jsx has no read-receipt display
today.

FRONTEND FILES THAT WILL CONSUME THIS API
-----------------------------------------
- src/components/pages/Admin/AdminPage.jsx
    (admin-alert-row renders the receipt summary inline + an
     expandable "Reads" drawer or button for the per-email detail)
- src/data/services/alertsService.js
    (add getAlertReads(alertId) helper)

DATA — NO SCHEMA CHANGES NEEDED
-------------------------------
Everything is derivable from the existing tables:
  - alerts                (target_type, target_emails, display_type)
  - alert_reads           (alert_id, user_id, read_at)
  - users                 (id, email)
For target_type='all' the "audience size" should match the same filter
the user-facing GET /api/v1/users/me/alerts uses — i.e. all users for
whom this alert would have been visible at the time of querying. A
reasonable v1 simplification: count = total active users (excluding
soft-deleted). Document whichever you choose.

ENDPOINTS
---------

(1) Extend GET /api/v1/admin/alerts response
    Add two aggregate fields to each alert row so the list view can
    render the headline number without N round-trips:
      {
        "id": 42,
        "subject": "...",
        ...,
        "read_count": 12,            // unique users in alert_reads
        "audience_size": 287         // see notes below
      }
    audience_size semantics:
      - target_type = 'all'      → count of users targetable today
      - target_type = 'specific' → length of target_emails
    audience_size MAY be null if computing it is expensive; the
    frontend will fall back to showing just "{read_count} confirmed".

(2) GET /api/v1/admin/alerts/{alert_id}/reads
    Auth: admin only (403 otherwise)
    Returns the per-recipient detail.

    For target_type = 'specific':
      [
        { "email": "a@b.com", "user_id": 12,   "read_at": "2026-05-14T18:22:00Z" },
        { "email": "c@d.com", "user_id": null, "read_at": null },
        { "email": "e@f.com", "user_id": 17,   "read_at": null }
      ]
      - One entry per address in target_emails
      - user_id = null if the email doesn't match a registered user
      - read_at = null if they haven't clicked "Got it"
      - Sort: read first (newest first), then unread alphabetical

    For target_type = 'all':
      {
        "read_count": 12,
        "audience_size": 287,
        "reads": [
          { "email": "a@b.com", "user_id": 12, "read_at": "2026-05-14T18:22:00Z" },
          ...
        ]
      }
      - "reads" is paginated/capped to the most-recent 200 to avoid
        dumping the entire user table in one response. The headline
        number (read_count) is the source of truth.

    Errors:
      403 { "detail": "Admin access required." }
      404 { "detail": "Alert not found." }

CLIENT BEHAVIOR
---------------
- The admin row already shows audience pill + type chip. For modal
  alerts it will add a small "{read_count} of {audience_size} confirmed"
  badge inline. Non-modal rows skip this entirely.
- Clicking the row (or a "View reads" affordance) opens a drawer that
  calls (2) and renders the per-recipient table.
- Real-time updates are NOT required for v1 — receipts refresh when
  the admin reopens the drawer or refreshes the page.

OPEN QUESTIONS
--------------
- Should deleting an alert (DELETE /api/v1/admin/alerts/{id}) also
  remove the read receipts? Today the CASCADE on alert_reads says yes.
  If admins ever want post-hoc audit, switch to soft-delete first
  (see Feature 1 open question on `deleted_at`).
- Privacy: per-recipient read data exposes user activity. Document
  the admin-only access; consider adding it to a future audit log.

FEATURE 2 — EMAIL CAMPAIGNS
============================================================

WHAT IT IS
----------
Admin composes an email (subject, body, optional CTA), picks an
audience segment (all / free / premium / weekly / monthly / annual /
lapsed), and sends. The frontend shows a recipient count, supports
test sends to the admin's own email, and displays a history of
past campaigns.

CURRENT STATE
-------------
Frontend is fully built — composer, audience picker, live preview,
test-send button, confirmation modal, recent-campaigns history.
All using mock counts and `MOCK_CAMPAIGN_HISTORY` from
src/data/constants/campaignsMockData.js. No emails actually sent.

FRONTEND FILES THAT WILL CONSUME THIS API
-----------------------------------------
- src/components/pages/Admin/CampaignsPage.jsx
- src/components/pages/Admin/AdminPage.jsx       (recent campaigns row)
- src/data/constants/campaignsMockData.js        (will be replaced)

EMAIL PROVIDER RECOMMENDATION
-----------------------------
Use Resend (https://resend.com). Free tier covers low volume,
modern API, simple webhooks. Postmark, SendGrid, AWS SES also fine.

DATA MODEL
----------
Table: campaigns
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid()
  subject         text NOT NULL
  body            text NOT NULL
  cta_label       text NULL
  cta_url         text NULL
  audience        text NOT NULL
                  CHECK (audience IN ('all','free','premium','weekly',
                                      'monthly','annual','lapsed'))
  recipient_count int NOT NULL DEFAULT 0  -- snapshotted at send time
  status          text NOT NULL DEFAULT 'sent'
                  CHECK (status IN ('sent','failed','draft'))
  sent_at         timestamptz NULL
  created_at      timestamptz NOT NULL DEFAULT now()
  created_by      uuid REFERENCES users(id)

Optional: campaign_recipients table if you want per-recipient
tracking (open/click/bounce) — Resend stores this on their side,
so for v1 you can skip it.

AUDIENCE RESOLUTION
-------------------
Map each `audience` key to a SQL filter:
  all      → users WHERE email_updates = TRUE
  free     → users WHERE email_updates = TRUE AND subscription_tier = 'free'
  premium  → users WHERE email_updates = TRUE AND subscription_tier = 'premium'
  weekly   → users WHERE email_updates = TRUE AND subscription_plan  = 'weekly'
  monthly  → users WHERE email_updates = TRUE AND subscription_plan  = 'monthly'
  annual   → users WHERE email_updates = TRUE AND subscription_plan  = 'annual'
  lapsed   → users WHERE email_updates = TRUE
                    AND subscription_status IN ('canceled','cancelled')

ALWAYS exclude users with `email_updates = FALSE` regardless of
audience selection. This is a hard CAN-SPAM/GDPR requirement.

ENDPOINTS
---------

(1) GET /api/v1/admin/campaigns
    Auth: admin only
    Returns: [{ id, subject, audience, recipient_count, sent_at, status }, ...]
    Sorted by sent_at DESC. Last 50 entries.
    Used by: AdminPage Campaign Manager row + CampaignsPage history.

(2) GET /api/v1/admin/campaigns/audience-counts
    Auth: admin only
    Returns:
      {
        "all":     412,
        "free":    287,
        "premium": 98,
        "weekly":  22,
        "monthly": 64,
        "annual":  12,
        "lapsed":  27
      }
    Used to populate the audience picker live counts.

(3) POST /api/v1/admin/campaigns/test
    Auth: admin only
    Body:
      {
        "subject": "...",
        "body": "...",
        "cta_label": "View Predictions",  // nullable
        "cta_url": "https://...",          // nullable
        "to_email": "admin@sandlotpicks.com"
      }
    Sends a single email to to_email. Does NOT create a campaign row.
    Response 200: { "ok": true }
    Errors:
      400 { "detail": "Subject is required." }
      502 { "detail": "Email provider unavailable. Try again." }

(4) POST /api/v1/admin/campaigns/send
    Auth: admin only
    Body:
      {
        "subject": "...",
        "body": "...",
        "cta_label": "View Predictions",
        "cta_url": "https://...",
        "audience": "free"
      }
    Behavior:
      a. Resolve audience to recipient list (filter by email_updates).
      b. Insert campaigns row with status='sent', sent_at=now(),
         recipient_count = len(recipients).
      c. Send to provider in batched calls (Resend: up to 100 per call).
      d. Use BCC or per-message send — never put all addresses in To.
      e. Append unsubscribe link automatically:
         https://www.sandlotpicks.com/unsubscribe?token=<jwt-or-uuid>
    Response 201:
      {
        "id": "uuid",
        "recipient_count": 287,
        "sent_at": "2026-04-28T15:00:00Z",
        "status": "sent"
      }
    Errors:
      400 { "detail": "Audience has no recipients." }
      400 { "detail": "Subject and body are required." }
      502 { "detail": "Email provider error: <provider message>" }

EMAIL TEMPLATE
--------------
Server should wrap user-supplied body in a branded HTML template:
  - Header: "⚾ Sandlot Picks" wordmark
  - Body: rendered with line breaks as <p> tags
  - CTA button (if provided): teal gradient, full-width, links to cta_url
  - Footer: small grey text with manage-preferences and unsubscribe links
The frontend preview at CampaignsPage.jsx uses this exact structure
as a reference — replicate it server-side.

UNSUBSCRIBE FLOW
----------------
Already exists at /unsubscribe in the frontend. Backend should
accept a one-click unsubscribe token from the email and set
users.email_updates = FALSE.

FEATURE 3 — AI ASSIST (LLM PROXY)
============================================================

WHAT IT IS
----------
The article editor and campaign composer have ✨ AI Assist
buttons that should call an LLM (Claude or GPT) to generate or
refine content. The frontend calls a single proxy endpoint —
the server holds the API key and tracks usage.

CURRENT STATE
-------------
Frontend uses pre-canned mock generators in:
  - src/components/pages/Admin/CampaignsPage.jsx
      → mockGenerateBody, mockSubjectIdeas
  - src/components/pages/Admin/ArticleEditor.jsx
      → mockTitleIdeas, mockSummaryDraft, mockBlockRefine

Each function returns hardcoded sample text after a 1.1s setTimeout.

WHY A PROXY (instead of frontend calling LLM directly)
------------------------------------------------------
- API keys must never live in the browser bundle.
- Lets you rate-limit per admin user.
- Lets you log usage / cost per admin.
- Lets you swap providers without redeploying frontend.

ENDPOINT
--------
POST /api/v1/admin/ai/generate
Auth: admin only
Body:
  {
    "task": "campaign_subject" | "campaign_body" |
            "article_title"    | "article_summary" |
            "article_block_refine",
    "context": {
      // task-specific fields below
    }
  }

Task-specific contexts:

  campaign_subject:
    { "audience": "free", "count": 5 }
    → returns array of 5 subject line strings

  campaign_body:
    {
      "audience": "premium",
      "current_body": "<existing draft or empty>",
      "instruction": "Announce that pitcher props are live"
    }
    → returns a single markdown body string

  article_title:
    {
      "summary": "<post.summary>",
      "content_text": "<flat-text version of all blocks>",
      "type": "article" | "blog",
      "count": 5
    }
    → returns array of 5 title strings

  article_summary:
    { "content_text": "<flat-text>" }
    → returns a single summary string

  article_block_refine:
    {
      "block_text": "<original text>",
      "block_type": "paragraph" | "heading" | "subheading" | "quote",
      "action": "improve" | "shorter" | "expand" | "casual" | "sharper",
      "instruction": "<optional custom prompt>"
    }
    → returns a single refined text string

Response shapes:
  Single string:  { "text": "..." }
  List of strings: { "texts": ["...", "...", "..."] }

Errors:
  400 { "detail": "Unknown task: <task>" }
  429 { "detail": "AI usage limit reached. Try again in 1 hour." }
  502 { "detail": "AI provider error." }

PROVIDER RECOMMENDATION
-----------------------
Anthropic Claude (claude-haiku-4-5 for speed/cost on the refine
tasks; claude-sonnet-4-6 for higher-quality summary/title work).
Pass the existing brand voice in a system prompt — punchy, data-
driven, baseball-fluent, no hype.

USAGE TRACKING (optional v1)
----------------------------
Log every call to ai_usage_log table:
  user_id, task, prompt_tokens, completion_tokens, cost_usd,
  created_at. Lets you see who's spending what over time.

FEATURE 4 — FREE WEEK PROMO ENFORCEMENT (FREE7)
============================================================

WHAT IT IS
----------
Free-tier users can claim one free week of premium access by
redeeming the FREE7 promo code on the Settings page. The flow
calls POST /api/v1/subscriptions/redeem-promo, redirects through
Stripe, and the user lands on /subscription/success as premium.

CURRENT STATE
-------------
The redemption flow itself is wired (you said you implemented
the endpoint server-side already). The remaining piece is making
sure each user can only claim ONCE.

WHAT THE CLIENT NEEDS
---------------------
The /api/v1/users/me response should include a new field:

  free_week_claimed_at: timestamptz | null

Frontend uses this to:
  - Hide the Free Week card on Settings once it's been claimed
  - Show "Free week already redeemed" state if they try again

CLIENT FILES THAT WILL CONSUME THIS
-----------------------------------
- src/context/AuthContext.jsx (mergeProfile reads it)
- src/components/pages/Account/SettingsPage.jsx (gates the card)

WHERE THE FIELD GETS SET
------------------------
Stripe webhook on `checkout.session.completed`:
  IF the redeemed coupon was the FREE7 code AND
     user.free_week_claimed_at IS NULL
  THEN UPDATE users SET free_week_claimed_at = NOW()

Defense-in-depth (don't rely only on the frontend hiding the card):
The /api/v1/subscriptions/redeem-promo endpoint should reject the
request with 400 { "detail": "You've already redeemed a promotional
code." } when free_week_claimed_at IS NOT NULL.

ALSO ON STRIPE'S SIDE
---------------------
Set on the FREE7 coupon:
  - max_redemptions_per_customer: 1
  - applies_to: weekly price only

This blocks the easy abuse of the same Stripe customer
re-redeeming the code.

FEATURE 5 — ACTIVE SESSION LIMIT (5 PER USER)
============================================================

WHAT IT IS
----------
Cap each user at a maximum of 5 active sessions. When a 6th login
happens (any device, any auth flow — login, refresh, OAuth, etc.),
the oldest session is automatically revoked so the new session
takes its slot.

CURRENT STATE
-------------
The Settings page already lists active sessions (Active Sessions
section) and lets users manually revoke any session via
`userProfileService.revokeSession(id)`. There is currently no cap.
The frontend now displays the message "Max 5 active sessions per
user — signing in on a 6th device will automatically end your
oldest session" and renders sessions sorted newest-first, but the
actual enforcement must happen server-side because:
  - Sessions are minted server-side at login/refresh; the client
    can't preempt the create.
  - Two near-simultaneous logins can both think they're #5.
  - Revoking client-side after the fact races with refresh-token
    requests already in flight from older sessions.

FRONTEND FILES THAT WILL CONSUME THIS
-------------------------------------
- src/components/pages/Account/SettingsPage.jsx (Active Sessions
  section — already mentions the 5-session cap to the user)
- src/data/services/userProfileService.js → getSessions(), revokeSession()
- src/data/services/userAuthService.js     → login(), refreshToken()

WHERE TO ENFORCE
----------------
Inside the function(s) that INSERT into the `sessions` table —
typically the login handler and any social/SSO callback. After
inserting the new session row, run:

  WITH ranked AS (
    SELECT id,
           ROW_NUMBER() OVER (ORDER BY last_active_at DESC, created_at DESC) AS rn
    FROM sessions
    WHERE user_id = :user_id AND revoked_at IS NULL
  )
  UPDATE sessions
  SET revoked_at = now(),
      revoked_reason = 'session_limit_exceeded'
  WHERE id IN (SELECT id FROM ranked WHERE rn > 5);

This keeps the 5 most recently active sessions and revokes the rest
in a single statement. Run this transactionally with the new
session insert so a race can't push the count over 5.

REFRESH-TOKEN BEHAVIOR
----------------------
When a refresh-token request comes in for a session that was
revoked by the cap, return 401 with:
  { "detail": "Session ended — too many active devices. Please sign in again." }
The frontend's AuthContext will catch the 401 from refreshToken,
clear local state, and redirect to /account.

OPTIONAL UX TOUCH
-----------------
On a successful login that triggered a cap-eviction, include a
small flag in the response:
  {
    "access_token": "...",
    "refresh_token": "...",
    "expires_in": 3600,
    "evicted_session": {
      "device_info": "Chrome on Mac",
      "last_active_at": "2026-04-22T11:14:00Z"
    }
  }
The frontend can display a toast: "Signed out your oldest session
(Chrome on Mac) — you've reached the 5-device limit."
(Not required for v1; the silent eviction is fine.)

CONFIGURATION
-------------
Make the cap a constant in the backend (e.g. SESSION_LIMIT = 5).
Future tier-based tweaks (e.g. premium users get 10) become a
one-line change.

CURRENT STATE

typing indicator, message history, premium auth gate, mobile
responsive. Mock responses are generated by `mockResponseFor(prompt)`
in ScoutAIChat.jsx using a simple keyword router that returns

FRONTEND FILES THAT WILL CONSUME THIS API
-----------------------------------------

  → swap mockResponseFor() for a real fetch (ideally streaming)
- src/components/pages/predictions/PredictionsNav.jsx
  → already includes the Scout AI tab

WHY A SERVER PROXY (vs frontend calling the LLM directly)
---------------------------------------------------------

- Server has the prediction data, odds, and Scout AI scouting reports
  needed to ground the LLM's answer in actual numbers.
- Per-user rate limiting and usage tracking live server-side.

ENDPOINT
--------
POST /api/v1/predictions/scout-ai/chat
Auth: premium users only (403 otherwise)
Body:
  {
    "messages": [
      { "role": "user",      "content": "What's the best pick of the day?" },
      { "role": "assistant", "content": "<previous answer>" },
      { "role": "user",      "content": "Tell me more about Skubal" }
    ]
  }
Response 200 (non-streaming v1):
  {
    "reply": "Based on tonight's slate ... <markdown-lite text>",
    "citations": [                       // optional but recommended
      { "type": "pitcher_prop", "game_pk": 123, "label": "Skubal Over 6.5 K" },
      { "type": "game",         "game_pk": 123, "label": "DET vs PIT" }
    ]
  }
Errors:
  401 { "detail": "Sign in required." }
  403 { "detail": "Scout AI is a premium feature." }
  429 { "detail": "Daily Scout AI limit reached. Try again tomorrow." }
  502 { "detail": "AI provider error. Please try again." }

STREAMING (v1.5)
----------------
For better UX, return a Server-Sent Events stream:
  Content-Type: text/event-stream
  data: { "delta": "Based on tonight's slate, here's my top pick:\n\n" }
  data: { "delta": "**Tarik Skubal — Over 6.5 K's**" }

FEATURE 7 — HERO IMAGE UPLOAD (FASTAPI PROXY → SUPABASE STORAGE)
============================================================

WHAT IT IS
----------
The article/blog editor's "Hero Image URL" field is currently a
URL-only text input. Admins want to upload an image directly from
their machine and have the resulting public URL filled in for them.

CURRENT STATE
-------------
- The Supabase Storage bucket `post-images` has been created
  (public reads enabled, 5 MB limit, allowed MIME types png/jpeg/
  webp/gif). No RLS policies are needed — see auth context below.
- Editor field at src/components/pages/Admin/ArticleEditor.jsx:837
  is a <input type="url"> that stores whatever the admin pastes.
- No Storage usage exists anywhere in src/ today.

AUTH CONTEXT (IMPORTANT — DRIVES THE DESIGN)
--------------------------------------------
The application uses **FastAPI-issued JWTs for auth**, not Supabase
Auth. The frontend Supabase client is created with the anon key
(public, in the bundle). `public.users.id` is an integer; nothing
exists in the database that ties a Supabase Auth UUID to an app
user. Consequences:

  - `auth.uid()` from RLS policies is always null on browser calls.
  - RLS policies attempting to gate by app-user identity will lock
    out everyone, not just non-admins.
  - The browser CANNOT be trusted to authorize its own uploads.

Therefore the upload MUST be proxied through the FastAPI server,
which already has admin verification (`get_current_admin_user`)
and the Supabase service_role key (already in .env — your existing
scripts/syncContentFromSupabase.js uses SUPABASE_SERVICE_ROLE_KEY).
The service_role key bypasses Storage RLS entirely, so the bucket
needs no extra policies beyond the implicit public-read behavior.

WHAT NEEDS TO BE DONE — A SINGLE FASTAPI ENDPOINT
-------------------------------------------------

(1) NEW ENDPOINT
    POST /api/v1/admin/upload
    Auth: admin only (use existing get_current_admin_user)
    Content-Type: multipart/form-data
    Form fields:
      file:   the binary image (required)
      kind:   "hero" | "block"  (optional, default "hero" — drives
                                 the storage path prefix)
      slug:   string (optional — used in the storage path for
                      human-readable layout, falls back to "misc")

    Behavior:
      a. Validate Content-Type starts with "image/" and is in:
           ["image/png", "image/jpeg", "image/webp", "image/gif"]
         else 400 { "detail": "Only PNG, JPEG, WebP, or GIF images
                              are allowed." }
      b. Validate file size <= 5 MB (5_242_880 bytes)
         else 400 { "detail": "Image must be 5 MB or smaller." }
      c. Build the storage path:
           {kind}/{slug or "misc"}/{epoch_ms}-{slugified_filename}
         where slugified_filename strips spaces/special chars and
         keeps the original extension. Example:
           hero/welcome-2026-season/1715800000000-banner.png
      d. Upload via Supabase Python client:
           supabase.storage
             .from_("post-images")
             .upload(path, file_bytes, file_options={"content-type": mime})
      e. Construct the public URL:
           {SUPABASE_URL}/storage/v1/object/public/post-images/{path}
         (or use supabase.storage.from_("post-images").get_public_url(path))

    Response 201:
      {
        "url": "https://xyz.supabase.co/storage/v1/object/public/post-images/hero/welcome-2026-season/1715800000000-banner.png",
        "path": "hero/welcome-2026-season/1715800000000-banner.png",
        "size_bytes": 184231,
        "content_type": "image/png"
      }

    Errors:
      400 { "detail": "<specific reason>" }
      403 { "detail": "Admin access required." }
      502 { "detail": "Storage upload failed: <provider message>" }

(2) NO DATABASE CHANGES
    The returned URL is written into the existing
    content_posts.hero_image_url column (text). No schema change.

(3) NO RLS POLICIES NEEDED
    Reads: bucket is already public.
    Writes: only the FastAPI server (with service_role) can write.
            Browser-side anon-key uploads to the bucket will be
            implicitly denied because no INSERT policy exists.
    This is the desired security posture for this stack.

(4) OPTIONAL — DELETE ENDPOINT (NOT REQUIRED FOR V1)
    Once content rotation is happening, an admin DELETE endpoint
    would let stale images be cleaned up:
      DELETE /api/v1/admin/upload  body { "path": "<storage path>" }
    Skip for v1; orphaned images can be cleaned up by a future
    sweep job that compares storage objects to content_posts.hero_image_url
    references.

FRONTEND CHANGES (HANDLED IN A FOLLOW-UP CHANGE, NO ACTION NEEDED)
------------------------------------------------------------------
Once the endpoint is live, the editor will:
  a. Add a small "Upload image" button next to the existing URL input.
  b. File picker (accept="image/*", 5MB max) → POST multipart to
     /api/v1/admin/upload with form fields { file, kind: "hero",
     slug: post.slug }.
  c. On success, set hero_image_url to response.url.
  d. Show inline upload progress + error states.
The existing URL input stays — admins can still paste an external URL.

CONFIRMATION TO SEND BACK
-------------------------
Reply with:
  - Endpoint deployed and reachable at /api/v1/admin/upload
  - Confirmation of the multipart contract above
  - The exact public URL pattern the endpoint returns (so the FE
    knows to expect the storage.../object/public/... form)
Once confirmed, the FE upload UI will be wired in a single follow-up.
